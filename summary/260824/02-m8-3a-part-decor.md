# M8-3a — 語句に貼り付く図形（帯・罫・枠）

2026-08-24 / [Issue #43](https://github.com/bubbleShaker/lyric-stage/issues/43)

## 何をしたか

今の画は**文字と背景しかなかった**。構図（M8-1）で語句は画面中を動き、書体（M8-2a）は極太になり、
配色と背景（M8-2）で地は引けた。それでも参考動画と並べて決定的に足りないのが**面と線**で、
文字PV では帯や罫は装飾ではなく**構図の一部**として働く（語句を画面に留め、視線の流れを作る）。

歌詞シートに `decor` を書けるようにして、語句に貼り付く 3 種類の図形を足した。

| 名前 | 見た目 | 色（役割） |
|---|---|---|
| `band` | 語句の後ろに敷く面。左右へ 0.28em はみ出す | `dim`（面・帯の地） |
| `rule` | 語句の下（縦組みなら左）を走る細い線 | `mute`（線） |
| `box` | 語句を囲む輪郭線。左から拭き取るように現れる | `mute` |

M8-2 で用意した明度の段が、役割名のとおりそのまま当てはまった。

## 決めた 3 つの分岐点

| 分岐点 | 決めたこと | 理由 |
|---|---|---|
| どこに描くか | **DOM**（canvas ではない） | 帯は語句に貼り付くので、canvas だと文字の実寸を毎フレーム測る羽目になる |
| データの持たせ方 | **`decor` = 直交する第 3 の軸** | 演出名に畳むと 7 演出 × 3 図形で爆発する |
| 動きの持たせ方 | **JS は進み具合だけ、意味は CSS** | 伸びる向きは組み方で変わる。両方に書くと判断が 2 か所になる |

### 1. なぜ canvas ではなく DOM か

背景（`GrainField`）は canvas なので、図形もそちらへ、が素直に見える。採らなかった。

帯や罫は**語句の大きさ・位置に貼り付く**もので、canvas に描くには DOM 側で組んだ文字の実寸を
毎フレーム測って同期することになる。座標系が二重になるだけでなく、
`getBoundingClientRect` を毎フレーム読むのは M5-1 で決めた
「毎フレームの `render` では `clientWidth` を読まない」と真っ向からぶつかる。

`.stage__frame`（構図の枠）の中に要素として置けば、位置も大きさも傾きも**ただ付いてくる**。
背景（canvas）と図形（DOM）を役割で分ける形にした。

```
.stage__frame     ← 構図（どこに・どのくらい・どの傾きで）
  .stage__decor   ← 図形（M8-3a）。文字より前に挿す＝奥に描かれる
  .stage__text    ← 文字。GSAP が動かすのはここだけ
```

### 2. なぜ `effect` に畳まないか

M8-1 で `place`（構図）を `effect`（動き）に畳まなかったのと同じ理由。
`bandZoom` のような名前を足していくと組み合わせが爆発する。

語彙（どんな名前が実在するか）は `stage/decor.ts` のレジストリが持ち、
`domain/lyrics.ts` は**形だけ**を見る（配列か・空でないか・重複していないか）。
`effect` と `place` で引いたのと同じ線。

**ただし `decor` だけは行から語句へ継がない。** `effect` / `place` は「この語句だけ変えたい」時に
書く上書きだが、図形は**置く語句を選ぶ**もの。行から配ると刻んだ行の全語句に同じ帯が出て、
画を締めるどころか埋めることになる。

### 3. JS は「どこまで進んだか」だけを持つ

図形のタイムラインがするのは `--decor-grow` を 0 → 1 に動かすことだけで、
**それが何を意味するかは CSS が決める**。

```
decor.ts    「band は 0.42 秒かけて 0 → 1 に進む」
style.css   「band にとって進むとは scaleX のこと（縦組みなら scaleY）」
```

伸びる向きは組み方で変わる（横組みは横へ、縦組みは下へ）。図形の形はもともと CSS が持っている
のだから、向きもそちらに寄せた方が破れない。副産物として `decor.ts` は「何秒で進むか」しか
知らずに済んでいる。

gsap はカスタムプロパティも動かせるが、**未設定のプロパティは開始値を読めない**
（`getPropertyValue` が空文字を返す）ので `from` ではなく `fromTo` で両端を書く。

## つまずいたこと

### 「木の順で奥に置く」は 3D では成り立たない（レビュー 🔴）

図形を文字より前（`text.before()`）に挿せば奥に描かれる、と考えていた。半分は正しい。
語句の枠は `transform-style: preserve-3d`（文字ごとの奥行きのため）なので、
**木の順が効くのは同じ奥行きにある間だけ**。

`rushIn` は文字を `z: -1400` から、`swing` は語句ごと `z: -260` から動かす。
その最中は**文字の方が帯より奥**にいるので、帯が語句を丸ごと隠す。
実際にその組み合わせがシートに 2 つ入っていた。

図形に `solid`（塗りか線か）を持たせ、シートの検査で「面 × 奥行きを動かす演出」を落とすようにした。
**どの演出が奥行きを動かすかは表に書かない** — 実際に組み立てて、トゥイーンが
`z` / `rotationX` / `rotationY` を触るかを見る（表にすると演出を足した時に更新を忘れる）。

割り当ては、面（`band`）を平面の演出（`zoom` / `glitch` / `bounce`）へ、
線（`rule` / `box`）を奥から迫る演出（`rushIn` / `swing`）へ寄せた。線なら潜っても実害が無い。

### 基準を「枠」に置いたら、別のページが 16px になった（レビュー 🔴）

図形は文字の**兄弟**なので、文字の `font-size` を継げない。継げないと余白を em で書けず、
大きさの段階（sm〜xl）に追従しない。そこで文字サイズの基準（`--size-base`）を
`.stage__text` から枠（`.stage__frame`）へ移した — これが間違いだった。

`font-preview.html`（書体を見比べる道具）は**構図の枠を意図的に立てず** `.stage__text` だけを使う。
基準が枠に移ると、このページの `font-size: calc(...)` は解決できず無効になり、
見本が 16px で並ぶ。しかも縦組みの見本だけは `.stage__text--vertical` が自前の基準を持つので
生き残るため、**横組みの 5 件だけが小さくなる**。書体を選び直す時に静かに誤った判断をする形だった。

置き場所を `:root` にして解決。「同じ clamp を 2 か所に書かない」という当初の狙いも保てている。

### 帯と罫がぴったり重なっていた（実測で発見）

帯は枠の下 8% まで、罫は下端から 4% あたりに来るので、両方を当てた語句で
罫が「帯の縁が少し明るいだけ」に見えていた。罫を枠の外（`-0.1em`）へ出して 11px 離した。

### 継がないと決めたのに、継がない指定が書けてしまう（レビュー 🔴）

刻んだ行に行の `decor` を書くと、検証も型も検査も通るのに**画には何も出ない**。
「継がない」判断は domain・組み立て・検査で一致していたが、
塞ぐべきは**その指定を書けてしまうこと**の方だった。`parseLyricLine` で弾くようにした。

### 画が見られない（環境）

この WSL では headless Chrome の `--screenshot` が固まる（`--dump-dom` は動く）。
そこで `getBoundingClientRect` を書き出させ、**実寸で**確かめた
（帯が文字の左右に 0.28em はみ出す / 帯と罫が 11px 離れる / 書いた順が奥から手前になる）。

**ただしこの確かめ方は平面の実寸しか見ない。** 上の 3D の重なりはここをすり抜けた。
奥行きが絡む噛み合わせは、実寸ではなく「演出が何を動かすか」を見て検査にするしかない。

なお `--dump-dom` を使うときは、**headless では rAF が回らない**のでタイマーで進める必要がある。

## 検査で止めていること

- 図形のクラス名が `style.css` に実在するか（基底クラスと縦組みの変種も含めて）
- 図形ごとに CSS 側が `--decor-grow` を読んでいるか（読み忘れると**タイムラインは動くのに画は静止**）
- 図形ごとに縦組みの変種の規則があるか（無いと横組みの向きのまま縦組みの語句に出る）
- 知らない図形名が書かれていないか（**全シート・全行**。未知の図形名は既定に落ちず完全に消える）
- 面の図形が奥行きを動かす演出の語句に当たっていないか
- 作品のどこかに図形が置かれているか（シートから消しても全緑のまま面と線だけが消えるため）

## 目で見て確かめてほしいこと

図形は**枠に固定**され、文字だけが演出で動く。この食い違いは実寸では出ないので、
再生して判断してほしい（どれもバグではなく画の判断）。

| 語句 | 組み合わせ | 見どころ |
|---|---|---|
| スター | `zoom` × 帯 | 文字が `scale: 3.4` から縮んで着地するので、**帯からはみ出す巨大な文字**が先に見える |
| 使える | `bounce` × 帯 + 罫 | 文字が `yPercent: 90` から上がるので、始まりの数コマは**帯の下にぶら下がる** |
| ネーション | `glitch` × 帯 | 散らし幅（`xPercent: ±60`）が帯のはみ出し（0.28em）を超えて**外へ飛ぶ**瞬間がある |
| シャイニング / 無限の | `rushIn` × 罫 / `swing` × 枠 | 線の**手前と奥が入れ替わる**（面ではないので隠れはしない） |

加えて 2 つ:

- **帯の色（`dim`）が弱すぎないか。** 地との差が小さいので、画で見て足りなければ段を上げる
  （`mute` は文字と競るので、その間の段を足すことになる）
- **縦組み × 図形は作品でまだ一度も出ていない。** 変種の存在は検査で担保しているが、
  見え方（左に走る罫、下へ伸びる帯）は未確認。区間を 7 行へ戻すとき、
  縦組みの行（`197.81` 切なさやトキメキが輝き出す）で一度通しておきたい
