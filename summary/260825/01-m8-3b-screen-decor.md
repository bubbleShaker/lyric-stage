# M8-3b — 画面に敷く図形（三分割の分割線・四隅のマーク）

2026-08-25 / [Issue #45](https://github.com/bubbleShaker/lyric-stage/issues/45)

## 何をしたか

M8-3a で**語句**には面と線が付いたが、**画面そのものには枠が無かった**。地（粒と光）の上に
語句と帯が浮いているだけなので、構図（M8-1 のアンカー 9 種）が画面のどこを基準に置かれて
いるのかが画から読めない。文字PV は画面を 1 枚のフレームとして扱い、分割線と四隅のマークが
その基準を可視化する。隅に寄せた語句が「何となくずれた配置」ではなく「絶妙に寄せた配置」に見える。

| 図形 | 見た目 | 濃さ |
|---|---|---|
| 分割線 | 画面を縦横それぞれ 3 つに割る 1px の罫（端から端まで） | `mute` の 16% |
| 四隅のマーク | 画面の四隅に置くかぎ括弧（2px の 2 辺） | `mute` の 50% |

**シートに口は無い。** 語句と一緒に動かない静的な装飾なので、持たせるのは置く仕組みだけ
（`mountScreenDecor(document.body)` を本編と `effect-preview.html` から 1 行ずつ）。

## 決めた分岐点

| 分岐点 | 決めたこと | 理由 |
|---|---|---|
| 密度 | **三分割の分割線**（全面の方眼ではない） | 線が密だと背景の粒と競り、極太 900 の文字の後ろが賑やかになる |
| どこに描くか | **DOM**（canvas ではない） | `Backdrop` の実装は自分で `clearRect` を呼ぶ。並べると後の層が前を消す |
| 実要素か擬似要素か | **実要素** | GSAP は擬似要素を直接動かせない。M8-4 が叩く先はここ |
| 誰が置くか | **`mountScreenDecor(parent)`** | 直書きだと同じマークアップが 2 ページに増える |

### 1. なぜ全面の方眼グリッドを採らなかったか

「グリッド」と書いてあったので方眼を敷くつもりだったが、線の本数がそのまま画の賑やかさになる。
M8-2 で粒の濃さに上限（0.22）を置いたのと同じ話で、**背景に属するものが極太 900 の文字と
同じ明度帯で競ると、文字PV ではなく「模様の上の文字」になる**。

縦横 2 本ずつでも「画面が枠として扱われている」ことは伝わる。三分割は構図の定石でもあるので、
アンカー（`top-left` / `middle-right` …）が置く位置ともそのまま噛み合う。

### 2. なぜ canvas ではなく DOM か（M8-3a と結論は同じ、理由は違う）

M8-3a の図形は語句に貼り付くので canvas だと実寸の同期が要った。**今回の図形は画面座標に
対して静的なので、その理由は効かない** — canvas に描いても結果は同じになる。

それでも DOM にしたのは層の後始末のため。`Backdrop` の実装はどれも自分で `clearRect` を
呼ぶので、素直に 2 つ並べると**後の層が前を消す**（M8-2 のレビュー指摘 🟡）。canvas に足すなら
`LayeredBackdrop` を作って「画面を消すのは誰か」を口の側で決め直す話になり、M8-3b が
背景の設計変更にまで膨らむ。DOM なら層の重なりはブラウザに任せられる。

```
canvas .backdrop     z-index: -1  ← 粒と光（M8-2）
div    .screen-decor z-index: -1  ← 分割線と四隅（M8-3b）。同じ段だが DOM 順で後
main   .stage                     ← 歌詞（語句の枠・図形・文字）
```

負の `z-index` の要素どうしは DOM の順で描かれるので、**後から足すだけで粒の上・歌詞の下**に入る。
`.stage` の中に入れないのは、あちらが「中の要素はすべて absolute である前提」で組まれているため
（通常の流れに乗る子を 1 つ足すと箱が伸び、アンカーの 7% / 10% の意味が静かにずれる）。

### 3. なぜ擬似要素にしなかったか

`.stage::before` と `::after` に持たせれば JS は一切要らず、マークアップの重複も起きない。
採らなかったのは M8-3a と同じ理由 — **GSAP は擬似要素を直接動かせない**（CSS 変数を経由する
迂回が要る）。次の M8-4 は「ビート同期の衝撃（フラッシュ・画面揺れ）」で、叩く先として
一番自然なのがまさにこの画面の図形になる。掴める形で置いておく。

`mountScreenDecor` はレイヤーを返す（今は捨てている）。M8-4 で取っ手が要るのはそこ。

## 検査で守ったこと

DOM の組み立てそのものは検査できない（jsdom 未導入）ので、**純粋な側と CSS との対応**に寄せた。

- **クラスが `style.css` に実在する**（M8-1 のレビュー指摘と同じ穴。打ち間違えても型検査も
  全テストも通り、起きるのは「その図形だけが出ない」という例外も警告も出ない壊れ方）
- **四隅がそれぞれ自分の 2 辺だけに線を引く。** 写し間違えて `top-right` が左の辺を引くと
  **かぎ括弧が内側を向く**。4 つ並んでいると向きの違いは目で追いにくい。置き場所
  （`top:` / `right:`）も同じ 2 辺かを併せて見る
- **マークの色がレイヤーから流れてくる。** 隅ごとの規則は色を書かず、レイヤーの
  `color: var(--stage-mute)` を `currentColor` で受ける。ここが落ちると四隅が
  `--stage-ink`（歌詞の色）で描かれるが、`palette.test.ts` は 16 進の直書きしか見ないので通る
- **`main.ts` と `effect-preview.html` が `mountScreenDecor` を呼んでいる**（`?raw` で読む）。
  この 1 行が消えても型検査も他の検査も全部緑のまま画面から図形だけが消える（M8-3a の
  「作品のどこかに図形が置かれている」と同じ穴）
- **class 属性に基底のクラスが入る。** 付け忘れると `position: absolute` が落ち、
  4 つのマークが通常の流れで左上に積み重なる
- **四隅の `edges` がクラス名と一致し、上下 1 辺 + 左右 1 辺になっている**

### レビューで塞いだ穴

🔴 **配線の検査が、それ自身の塞ごうとした穴を持っていた。** CSS 側は先例どおり
`css.replace(/\/\*[\s\S]*?\*\//g, '')` してから走査していたのに、`main.ts?raw` は素の文字列に
当てていた。つまり **`mountScreenDecor(document.body);` を消して
`// TODO: mountScreenDecor(...) は M8-4 で` と書き換えるだけで緑のまま通る**。
このリポジトリはコメントで関数名を名指しする流儀（`screen-decor.ts` の docblock 自体が
`mountScreenDecor(parent)` と書いている）なので、まさに起こりうる形だった。

🟡 ほかに 3 つ:

- **重なりの順が宣言に現れていなかった。** `.backdrop` も `.screen-decor` も `z-index: -1` で、
  正しい順序は「`main.ts` が canvas より後に敷く」ことでしか保証されていなかった。破れても
  例外も検査の赤も出ず、分割線が粒の下に沈むだけ。`.backdrop` を `-2` に下げて宣言に残した
- **配線の検査を `stage/` に置いていた。** `main.ts` は合成する側、`stage/` は合成される側なので、
  依存の向きがテストの中で逆流していた。`src/wiring.test.ts` に移し、ついでに
  `effect-preview.html`（tsconfig の外で型検査もテストも届かない）も見るようにした
- **`edges` とクラス名の整合を誰も見ていなかった。** 突き合わせていたのは「定数 ↔ CSS」だけで、
  `--top-right` に `edges: ['top', 'left']` と書いて CSS もそれに合わせれば全部緑で通る
  （`ScreenMark` の JSDoc が恐れている壊れ方そのもの）

## 目視について分かったこと

**Windows 側の Chrome なら headless のスクリーンショットが撮れる。**

```
"/mnt/c/Program Files/Google/Chrome/Application/chrome.exe" --headless --disable-gpu \
  --window-size=1280,720 --screenshot="C:\\...\\shot.png" "C:\\...\\page.html"
```

PLAN に「この WSL では headless の `--screenshot` が固まる」と書いたのは WSL 側に入れた
Chrome の話だった。`/mnt/c` のパスを Windows 形式で渡せば普通に撮れる。M8-3a で
`getBoundingClientRect` を書き出させて実寸で確かめたような迂回は、今後は要らない。

ただし**ウィンドウ幅は 500px より狭くできない**（`--window-size=390` を渡しても
`innerWidth` は 500 になる）。狭い画面の確認にはこの手は使えない。

## 残した宿題

- **濃さ（0.16 / 0.5）と間合い（`3.2vmin`）は 1280×720 と 500×900 で見て決めた値。**
  実際の背景（粒と光）は盛り上がりで明るさが変わるので、曲を流しながら見て詰め直す余地がある
- **`mountScreenDecor` の DOM の組み立ては未検査**（M8-1 で残した `appendPart` の宿題と同じ束）。
  jsdom を入れるかは [Issue #29](https://github.com/bubbleShaker/lyric-stage/issues/29) に続く
